webmcp-agent — 收斂邊界架構審查報告

產出時間：2026-08-27 ・ 分析範圍：目前工作樹的 Vite React SPA、WebMCP bridge、Chat/IndexedDB persistence 與 local LLM integration

依據：AGENTS.md、PLAN.md、目前 source 與 git checkpoint history；未找到正式 ADR、OpenAPI 或 WebMCP schema 文件，未標為「明確契約」的部分均是程式碼推斷。

結論先行

目前的收斂邊界大致符合問題規模：單一瀏覽器 SPA、單一 Chat flow、iframe-only WebMCP 與 IndexedDB persistence，沒有證據支持拆成後端服務或微服務。主要風險不在模組數量，而在跨模組共享的可變 context 與重複的持久化 identity。

建議優先修正兩個一致性缺口：將「一次 user input 的 bridge/agent context」變成不可變 snapshot；明確定義 siteId 與 url 的權威關係並加入 URL drift recovery。其次統一 theme state authority。其餘拆分應等待真實 change coupling 或需求出現。

審查範圍與判斷尺度

  • 架構尺度：module / single-application；不是 distributed-system redesign。
  • 核心 change drivers：WebMCP browser integration、Chat/thread lifecycle、local LLM transport、presentation/UI。
  • 品質屬性：目前最相關的是 Reliability、Modifiability、Testability、Security；未見流量或團隊資料，因此不對 Scalability/組織邊界作過度推論。
  • git history 顯示最近以 checkpoint 逐步收斂到 multi-site thread 與 iframe context，說明現有 feature boundary 是實際變更驅動形成，而非純資料夾分類。

收斂判斷

  • 合理：assistant 是 application orchestration boundary，負責 route、thread lifecycle 與 user flow；webmcp 負責 iframe capability discovery/execution。兩者協作不等於應合併。
  • 需要補強：webMcpBridge 是 module-level singleton，卻同時承載 frame identity、discovery state、special prompt state 與 executor。這是明確的生命週期/一致性邊界，不能只靠資料夾名稱保護。
  • 不建議：目前沒有理由引入 service/repository/interface 多層或後端；那會增加 deployment、failure 與 contract cost，卻不解決現有 snapshot/invariant 問題。

資料模型判斷

  • siteLastThreads 是明確的一對一 pointer consistency boundary，且 create/save 已使用 transaction，這是目前設計的強項。
  • ChatThread.siteId 與 ChatThread.url 同時保存，而 registry 另有 WebMcpSite.url，形成跨持久化/程式碼的雙重來源；這是本審查的主要 invariant 風險。

以下 ADR 是依目前程式碼反推的草稿，並非原作者已確認的決策；需人類補充或修正。

ADR-001：以單一 SPA 保持 WebMCP agent 的 application boundary（草稿）

背景：專案是純前端 Vite app，核心能力是瀏覽器中的 Chat、iframe tool bridge 與 local LLM；沒有後端部署、跨團隊 ownership 或高流量證據。

選項：1. 維持 single SPA：低部署與 network complexity，但共享 runtime state 要靠 lifecycle contract。2. 拆成 backend/API：可隔離 server policy，但增加 deployment、API contract、failure handling。3. 微服務：不符合目前規模與需求。

選擇：維持 single SPA，按 change driver 保持 assistant/webmcp/persistence 的 module boundary。

取捨：換得最低必要複雜度與較小 change surface；代價是 bridge singleton 與 browser lifecycle 必須被明確測試。

ADR-002：以 iframe 當次暴露能力作為 tool boundary（草稿）

背景：AGENTS 明確要求 Chat 只使用當下 iframe 暴露的 tools，且 executor 必須回到同一 frame context。

選項：1. bridge snapshot + captured executor：保持 iframe-only boundary。2. 將 tools 複製到 app registry：較容易測試，但會脫離實際網站能力。3. app 自帶 filesystem/network tools：違反 scope 與安全邊界。

選擇：保留 iframe-only bridge，補強 immutable context snapshot 與 origin contract。

取捨：換得網站能力與 Agent schema 一致；代價是 browser API availability、跨來源政策與 frame lifecycle 需要明確處理。

目前已收斂

single SPA、feature-based assistant/webmcp/persistence boundary、iframe-only tools、per-site last-thread pointer、每次 input 建立 ToolLoopAgent。

目前未收斂

bridge context 的跨 async operation 一致性、thread site URL authority、theme provider authority；這些是後續最小有效改善區域。

本次不建議新增

後端/Hono、微服務、event bus、Repository/Service interface 多層、跨來源 adapter。現有資料不足以證明它們解決當前問題。
