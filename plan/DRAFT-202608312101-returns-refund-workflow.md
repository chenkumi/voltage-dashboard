# Draft: Returns／Refund Approvals 統一流程重構

狀態：全部確認，可交付 `create-plan`

## 查證依據

- `src/app/webmcp/returns/return-pages.tsx`：目前 RMA 詳細頁同時呈現資格、物流、
  驗貨、退款計算、庫存處置、退款執行與 Agent 審查草稿。
- `src/app/webmcp/returns/return-state.ts`：目前畫面階段由多組狀態推導，但沒有提供
  Returns 與 Refund Approvals 共用的完整流程呈現模型。
- `src/app/webmcp/returns/return-editor-controller.ts`：目前審查草稿只保存在前端
  controller 記憶體，沒有正式備註實體、階段、經手人或持久化紀錄。
- `src/app/webmcp/returns/refund-approval-pages.tsx`：Refund Approval 是獨立詳細頁，
  顯示退款計算、核准及執行提示。
- `docs/RETURNS-RMA-SYSTEM-MODEL.md`：核准退貨、收貨、驗貨、退款核准與退款結果皆為
  人工最終操作；WebMCP 只提供安全查詢、導覽、分析與可逆草稿。

## 變更項目 1：統一售後狀態流程（類型：狀態流程）

### 之前

```text
退貨申請
   ↓
RMA 詳細頁
   ├─ 資格審查
   ├─ 物流收貨
   ├─ 驗貨
   ├─ 退款計算
   ├─ 庫存處置
   ├─ Agent 審查草稿
   └─ 退款執行
          ↕
   Refund Approvals 詳細頁
   ├─ 退款計算
   ├─ 核准決定
   └─ 退款執行提示
```

目前各區塊在 RMA 詳細頁並列呈現，Refund Approvals 又重複部分資訊，使用者不容易判斷
目前步驟、前置條件與下一個必要動作。

### 之後

```text
1. 退貨申請
   草稿 → 提交
          ↓
2. 資格審查
   審查中 ─→ 要求補件 ─→ 回到審查中
      ├──→ 拒絕 → 結案
      └──→ 核准退貨申請
                 ↓
3. 等待寄回／收貨
   等待寄回 ─→ 逾期 → 結案或人工處理
      └──→ 登記收貨
                 ↓
4. 驗貨
   尚未開始 → 驗貨中 → 完成驗貨
                          ├─ 全數拒絕 → 無退款結案
                          └─ 有通過品項
                                 ↓
5. 退款計算
   依驗貨結果產生固定金額
      └──→ 送交退款核准
                 ↓
6. 退款核准
   待核准
      ├──→ 退回修正 → 回到退款計算
      ├──→ 拒絕 → 無退款結案
      └──→ 核准
                 ↓
7. 退款執行
   等待外部退款
      ├──→ 失敗 → 等待重試
      └──→ 成功 → RMA 完成
```

驗貨重新開啟時：

```text
已完成驗貨
   ↓ 重新開啟
原退款計算與核准失效
   ↓
驗貨 → 重新計算 → 重新送審
```

庫存處置不是退款主流程的一個階段，而是驗貨完成後的平行工作：

```text
完成驗貨
   ├─ 退款計算／核准／執行
   └─ 重新入庫／瑕疵品／報廢／退回顧客
```

差異：建立一套由 Returns 與 Refund Approvals 共用的七階段流程；所有操作依前置狀態
解鎖，退回、失效、拒絕、重試及無退款結案皆有明確回流或終止位置。

使用者確認：已確認（2026-08-31）

## 變更項目 2：模組責任（類型：狀態流程／UI）

### 之前

- Returns 承擔 RMA 主檔，但在同一頁同時呈現所有階段。
- Refund Approvals 像獨立流程，重複顯示退款依據與退款執行提示。
- Agent 審查草稿被當成獨立 UI 區塊，使人工流程看起來依賴 Agent。

### 之後

| 模組 | 責任 |
| --- | --- |
| Returns | RMA 主檔及完整流程；處理申請、資格、收貨、驗貨、計算與退款執行。 |
| Refund Approvals | 第 6 階段的人工工作佇列；只能核准、退回或拒絕固定計算。 |
| 審查紀錄／備註 | 屬於 RMA，依階段保存多位經手人的紀錄，不屬於 Agent。 |
| WebMCP | 查詢、導覽、讀取流程狀態及填寫目前帳號的可逆備註草稿。 |
| Agent | 系統外部的選用操作者，不出現在人工流程設計中。 |
| 人工使用者 | 執行提交、資格決定、收貨、驗貨、送審、核准及退款結果等最終操作。 |

兩個詳細頁使用相同的流程定義：

- RMA 詳細頁顯示完整流程，但只展開目前待辦。
- Refund Approval 詳細頁顯示相同流程，但只操作第 6 階段。
- 核准完成後回到 RMA 處理第 7 階段。
- 不建立 Agent 專屬區塊或人工 UI 中的 Agent 呼叫入口。

差異：Refund Approvals 成為 RMA 流程中的明確工作階段，而不是平行系統；人工系統可在
沒有 Agent 的情況下完整運作，WebMCP 只暴露既有安全能力。

目前所有階段同時展開，完成、目前與尚未開始的內容具有相近視覺權重；動態下一步位於頁首，
但操作依據分散在其他區塊。庫存處置也與退款主流程並列，Agent 審查草稿則位於流程中央。

### 之後

```text
+----------------------------------------------------------+

+--------------------------------------+-------------------+

+----------------------------------------------------------+

+----------------------------------------------------------+

```

「目前待辦」依階段顯示唯一主要工作：

| 階段 | 目前待辦 |
| --- | --- |
| 1. 退貨申請 | 檢查申請內容並提交。 |
| 2. 資格審查 | 核准退貨申請、要求補件或拒絕。 |
| 3. 等待寄回／收貨 | 登記收到的包裹與收貨結果。 |
| 4. 驗貨 | 開始或繼續逐品項驗貨。 |
| 5. 退款計算 | 產生計算，確認版本後送交核准。 |
| 6. 退款核准 | 顯示等待狀態並開啟 Refund Approval；不能在 RMA 頁核准。 |
| 7. 退款執行 | 記錄外部退款成功、失敗或重試結果。 |

歷史與例外操作規則：

- 已完成階段預設收合但可查看；未到達階段只顯示解鎖條件，不顯示操作表單。
- 所有主要操作集中在「目前待辦」，不再同時出現在頁首與階段卡片。
- 「重新開啟驗貨」是驗貨歷史中的次要操作，執行前明示會使退款計算與核准失效。
- 核准退回後，第五階段重新成為目前待辦；退款失敗仍停留第七階段等待重試。
- 庫存處置獨立呈現為平行作業，不列入七階段主流程。

差異：RMA 詳細頁由「所有功能並排的控制台」改為「狀態驅動的案件工作頁」，使用者進入
頁面後能直接辨識目前階段、唯一主要工作、已完成依據與平行作業。

## 變更項目 4：審查紀錄／備註模型（類型：UI／資料格式／狀態流程）

### 之前

目前 `ReturnReviewDraft` 是只存在前端 controller 記憶體中的 Agent 專屬草稿：

```ts
ReturnReviewDraft {
  evidenceCodes
  operationalSummary
  nextStep
  supportDraft
}
```

- 沒有正式紀錄 ID、RMA 階段、作者、版本、發布狀態或持久化資料。
- 草稿內容與人工案件流程沒有正式整合，頁面重新載入後可能遺失。
- 「Agent 審查草稿」命名暗示案件必須經過 Agent，且客服回覆被混入內部審查內容。
- 無法支援多階段、多人經手、交接、修正及稽核。

### 之後

建立屬於 RMA 的通用審查紀錄／備註實體；人工使用者可直接使用，Agent 只能透過
WebMCP 代目前登入帳號填寫相同的可逆草稿：

```ts
ReturnReviewNote {
  id
  rmaId
  stage:
    | "return_request"
    | "eligibility"
    | "receipt"
    | "inspection"
    | "refund_calculation"
    | "refund_approval"
    | "refund_execution"
  category:
    | "review_recommendation"
    | "internal_note"
    | "handoff"
  content
  recommendation?:
    | "approve"
    | "request_information"
    | "reject"
  evidenceCodes?: string[]
  authorUserId
  status: "draft" | "published"
  createdAt
  updatedAt
  publishedAt?
  version
  inputSource: "ui" | "webmcp"
  supersedesNoteId?
}
```

其中 `inputSource` 只供稽核，不用於建立 Agent 專屬流程，也不在人工介面顯示
「Agent 審查」標籤。

草稿與發布規則：

- 每個 `(rmaId, stage, current user)` 最多一份有效草稿。
- 草稿自動儲存至 repository，不使用會阻塞瀏覽器自動控制的離頁 alert。
- 只有草稿擁有者可以繼續編輯、捨棄或發布；其他使用者只能看到已發布紀錄。
- Agent 經 WebMCP 寫入的就是目前登入帳號的同一份草稿，不建立第二套 Agent 資料。
- 已發布紀錄不可覆寫；修正時新增紀錄並以 `supersedesNoteId` 指向被修正紀錄。
- 案件進入新階段時，舊階段未發布草稿仍保留，供原作者稍後恢復或捨棄。
- 備註不改變 RMA 狀態、不等同正式決策，也不使退款計算或核准失效。
- 發布時由案件時間軸記錄事件中繼資料與 note ID，不把完整備註內容複製到時間軸。
- 客服回覆不再是備註的必要欄位；若日後需要對客溝通，應另建獨立功能與權限邊界。
- WebMCP 不得讀取其他使用者的私人草稿，也不得藉備註介面公開所有內部紀錄。

頁面呈現：

```text
+----------------------------------------------------------+
| 審查紀錄與備註                         [階段：目前階段 v] |
+----------------------------------------------------------+
| 我的草稿（自動儲存）                                     |
| 類型 [審查建議／內部備註／交接 v]                        |
| 建議 [核准／要求補件／拒絕 v]（僅審查建議顯示）          |
| 證據代碼 [.........................]（選填）             |
| 內容     [.........................................]     |
|          [.........................................]     |
| 已於 21:18 自動儲存 · 版本 3 · 僅目前帳號可見            |
| [捨棄草稿]                              [加入審查紀錄]   |
+----------------------------------------------------------+
| 已發布紀錄                                               |
| 驗貨 · 內部備註 · 王小明 · 20:41                         |
| <備註內容>                                               |
| -------------------------------------------------------- |
| 資格審查 · 審查建議：核准 · 陳大華 · 18:10              |
| <備註內容與證據代碼>                                     |
+----------------------------------------------------------+
```

若目前帳號在舊階段仍有未發布草稿，頁面以非阻塞提示顯示：

```text
你在「驗貨」階段有一份未發布草稿。 [繼續編輯] [捨棄]
```

正式的資格核准、驗貨完成、送交退款核准、核准決定及退款結果等業務操作仍位於
「目前待辦」，不得由發布備註代替。

差異：把無持久化、Agent 專屬的單人筆記改為人工流程原生的多人、多階段審查紀錄；
WebMCP 僅安全填寫目前帳號可逆草稿，發布備註與正式業務決策保持分離。

```text
[開啟 RMA 並重新計算]

拒絕後：
⑥退款核准：已拒絕 → 流程結案
⑦退款執行：不適用
此核准單已結束，不能再次決策。
拒絕原因／決策人／時間
[開啟 RMA]

因重新驗貨而失效：
④驗貨 ●目前
⑤原計算：已失效
⑥APR-2008：已失效
⑦待解鎖
此頁只保留歷史核准快照，不能再次決策。
[開啟 RMA 查看目前待辦]
```

RMA 與 Refund Approval 共用同一份七階段定義及狀態推導：

```ts
ReturnWorkflowStage {
  id
  label
  state:
    | "completed"
    | "current"
    | "attention"
    | "upcoming"
    | "terminal"
    | "not_applicable"
  detail
  destination?
}
```

共用規則：

- RMA 頁顯示完整流程並操作目前階段。
- Refund Approval 頁只操作第 6 階段，但可顯示整體進度。
- 退回後第 5 階段成為目前階段。
- 拒絕後第 6 階段成為終止點，第 7 階段標示不適用。
- 核准後第 7 階段成為目前階段，但只能回 RMA 操作。
- 重新驗貨會讓舊計算及核准單顯示失效。
- 已失效或已決策的核准單一律唯讀，不允許重複決策。

差異：Refund Approval 成為明確的第 6 階段人工決策工作頁，只負責審查固定計算；退款
執行回歸 RMA。兩個詳細頁共用同一套七階段流程與例外狀態。

建立或更新目前帳號草稿：

```ts
apply_my_return_note_draft({
  rmaId: "RMA-2008",
  stage: "refund_approval",
  expectedVersion: 2,
  category: "review_recommendation",
  recommendation: "approve",
  evidenceCodes: ["INSPECTION_ACCEPTED"],
  content: "驗貨數量與固定退款計算一致。"
})
```

欄位與執行規則：

- `rmaId` 必須與目前頁面一致，`stage` 必須是目前頁面允許填寫的階段。
- `expectedVersion` 防止覆蓋較新的人工修改；新草稿使用 `0`。
- `recommendation` 只可用於 `review_recommendation`；`evidenceCodes` 選填且只能引用
  系統實際提供的代碼。
- `content` 只接受安全營運文字，不得包含個資、付款資料或敏感憑證。
- `authorUserId` 與 `inputSource: "webmcp"` 由系統根據登入狀態寫入，Agent 不可指定。
- 工具只自動儲存可逆草稿，不發布備註，也不觸發案件狀態轉換。
